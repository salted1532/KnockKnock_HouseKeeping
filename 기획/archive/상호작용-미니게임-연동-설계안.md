# 상호작용 · 미니게임 연동 설계안

`기능정의서.md`의 SYS-01~06, 10을 실제로 어떻게 하나의 시스템으로 엮을지에 대한 구조 제안. 확정안이 아니라 구현 착수 전 검토용 초안.

## 1. 문제 정의

기능정의서는 SYS-01(오브젝트 상호작용), SYS-03(접객 대화), SYS-04(신분증 확인), SYS-05(승인/거절), SYS-10(탐문)을 각각 별개 항목으로 나열하지만, 실제로는 전부 "플레이어가 오브젝트/NPC를 상호작용 → 판단 미니게임 진입 → 결과가 이후 시간대에 영향"이라는 같은 흐름을 공유한다. 이걸 각각 따로 구현하면 시스템 4~5개가 서로 다른 방식으로 UI를 열고 닫고 결과를 저장하게 되어 유지보수가 어려워진다. 어떤 공통 구조로 묶을지가 이 문서의 핵심.

## 2. 레퍼런스 게임 조사

기획서(`넉넉하우스키핑.txt`)가 직접 언급한 4개 게임을 기준으로, "상호작용 → 미니게임 → 결과 반영"을 어떻게 연결하는지 조사.

| 게임 | 진입 방식 | 미니게임 형태 | 결과 반영 시점 |
|---|---|---|---|
| **Papers, Please** | 부스 창구에 서류가 도착 | 화면 전체가 서류 대조 전용 뷰로 전환(월드 이동 불가). 여권/입국서류를 클릭해 확대, 자를 대고 숫자 비교, 스탬프로 승인/거절 | 그 자리에서 즉시(스탬프) + 하루 끝 정산에서 급여/위반 페널티로 누적 반영 |
| **That's Not My Neighbor** | 문 앞 벨/노크 | 슬라이드 창구 너머로 얼굴·귀·눈동자 수 등을 체크리스트와 대조하는 전용 UI | 그 자리에서 입장 여부 결정 + 이후 날짜에 가족 반응/후속 이벤트로 지연 반영 |
| **No, I'm Not a Human** | 창문/문 두드림 | 커튼 젖히기 등으로 방문자를 관찰하는 클로즈업 뷰, 특징 체크 후 문 열지 결정 | 즉시 입장 여부 결정 + 동거인 상태(신뢰도 등)에 지연 반영 |
| **This War of Mine** | 낮/밤 페이즈 전환 | 미니게임이라기보다 선택지 팝업(대화창)형 이벤트 | 캐릭터 상태(허기/부상/사기)에 누적 반영, 밤 페이즈에서 결과가 드러남 |

**공통 패턴 4가지**

1. **진입 트리거와 판정 로직이 분리됨** — 문/창문/벨은 그냥 "미니게임을 여는 스위치"일 뿐이고, 실제 대조·판단 로직은 전용 오버레이 화면 안에서 처리된다.
2. **오버레이가 열리면 월드 이동/상호작용이 완전히 잠긴다** — 미니게임 진행 중에는 플레이어 컨트롤이 죽고 오버레이 UI만 입력을 받는다.
3. **판정 결과는 그 자리에서 소비되지 않고 데이터로 저장된 뒤, 다른 시간대(밤 정산/다음날 대화)에서 다시 참조된다.** 즉 신분증 확인 시스템과 승인/거절 시스템은 사실상 하나의 오버레이가 만들어낸 같은 결과값을 다른 시점에 두 번 쓰는 것.
4. **하루 전체를 감싸는 상위 페이즈 관리자가 각 미니게임이 언제 열릴 수 있는지를 통제한다** (Papers Please의 근무시간, TWoM의 낮/밤).

이 4가지가 그대로 이 프로젝트의 SYS-01/03/04/05/10 관계와 일치한다. 즉 새로 발명할 필요 없이 검증된 구조를 그대로 가져오면 된다.

## 3. 현재 코드가 이미 가진 것 / 빠진 것

- `Interactable.cs`는 enum-switch로 동작을 분기하는 구조라, 새 진입 트리거(예: "체크인 접수대 상호작용")를 추가하는 게 어렵지 않다. 이미 `Generic` 타입 + `UnityEvent onInteract`가 있어서, **씬에서 오브젝트에 이벤트 연결만 하면 코드 수정 없이 새 오버레이를 열 수 있다.** (Push 타입을 카트에 쓴 것과 같은 방식.)
- `InteractionOutline.cs`는 레이캐스트로 감지한 대상에 E키가 눌리면 무조건 `Interact()`를 호출한다. **오버레이(대화창, 신분증 확인창 등)가 열려 있는지 모른다.** 오버레이 UI가 떠 있는 상태에서 E를 누르면 뒤에 있는 오브젝트와 또 상호작용하는 버그가 날 수 있음 — 최소한의 가드가 하나 필요하다.
- `InventorySystem.cs`는 싱글톤 `Instance` + 고정 배열 슬롯 구조로, 인터페이스나 상태 클래스 없이 절차적으로 작성되어 있다. **이 스타일을 새 매니저(페이즈 관리자, 대화 시스템 등)에도 그대로 따라가는 게 일관성 있다.** 별도 아키텍처 레이어를 새로 도입할 필요 없음.

## 4. 제안 구조

새 클래스 3개만 추가하고, 나머지 미니게임들은 전부 그 위에 얹는다.

```
[SO_Guest 데이터] ← IDCheckOverlay가 참조
       │
Interactable(Generic) --onInteract--> OO Overlay.Open()
                                          │
                                   OverlayGate.IsOpen = true  (InteractionOutline이 이걸 보고 E 무시)
                                          │
                                   (오버레이 내부에서 판단/대화 진행)
                                          │
                                   StoryFlags.Set("guest3_approved", true)
                                          │
                                   OverlayGate.IsOpen = false
                                          │
                              DayPhaseManager.CompleteCurrentTask() 등으로 진행 체크
```

### 4-1. `StoryFlags` (싱글톤, `Dictionary<string, object>` 하나)
신분증 판정 결과, 탐문으로 얻은 단서, 승인/거절 여부 등 시스템 간에 공유되는 값을 전부 여기 문자열 키로 저장한다. 매 기능마다 새 매니저를 만들지 않고 이 딕셔너리 하나로 연결한다.
- `Set(string key, ...)` / `Get(string key)` 두 메서드면 충분. ScriptableObject나 이벤트버스 도입 불필요.

### 4-2. `OverlayGate` (싱글톤, `bool IsOpen` 하나)
오버레이(신분증 확인, 대화, 태스크 상세 등)를 여닫는 진입점에서 `OverlayGate.IsOpen`을 true/false로 세팅. `InteractionOutline.Update()` 맨 앞에 `if (OverlayGate.IsOpen) return;` 한 줄만 추가하면 됨.

### 4-3. `DayPhaseManager` (싱글톤, enum 상태 하나)
`enum DayPhase { Morning, Noon, Evening, Dawn, Sleep }`. 현재 페이즈를 들고 있고, `NextPhase()` 하나로 다음 시간대로 넘긴다. SYS-02 태스크 전부 완료, SYS-06 배정 완료 등 "다음으로 넘어갈 조건"은 각 시스템이 `DayPhaseManager.Instance.ReportTaskDone(id)`처럼 보고하는 방식으로 느슨하게 연결.

이 3개는 각각 50줄 안팎이면 되는 수준 — `InventorySystem.cs`와 비슷한 무게.

## 5. 시스템별 적용

- **[SYS-04 신분증 확인] + [SYS-05 승인/거절] → 사실상 하나의 오버레이로 통합 제안.** `IDCheckOverlay`가 신분증 클로즈업 + 예약자 명단을 같은 화면에 띄우고, 대조 끝나면 승인/거절 버튼 자체가 결과. 별도 시스템 두 개로 나눌 이유가 없음 — Papers Please도 대조와 스탬프가 한 화면.
- **[SYS-03 접객 대화] + [SYS-10 탐문] → 같은 `DialogueOverlay` 재사용.** 기능정의서에도 이미 "탐문은 SYS-03을 재사용"이라고 적혀 있음. 대화 트리 데이터에 트리 ID만 다르게 넣는 구조면 됨.
- **[SYS-02 태스크 체크리스트] → 오버레이 불필요.** 청소/정비는 월드에서 바로 끝나는 상호작용이라 `Interactable.Generic`의 `onInteract`에 `DayPhaseManager.Instance.ReportTaskDone("fence_repair")` 같은 호출만 연결하면 끝. 체크리스트 UI는 HUD에 상시 표시(오버레이 아님, SYS-12 HUD 쪽에 속함).
- **[SYS-06 객실 배정] → `IDCheckOverlay`의 승인 결과 직후 같은 흐름에서 이어지는 리스트 UI.** 별도 오버레이라기보다 승인 버튼을 누른 다음 단계로 취급.

## 6. 하지 말아도 되는 것

- `IInteractable` 인터페이스나 오브젝트별 서브클래스 — 지금처럼 `Interactable` 하나에 enum 케이스 추가하는 걸로 SYS-01~06 전부 커버 가능. 케이스가 15개 넘어가면 그때 분리 고민.
- 이벤트버스/메시징 프레임워크 — `StoryFlags` 딕셔너리 하나로 충분한 규모.
- 대화 데이터를 위한 커스텀 그래프 에디터 — 노드 리스트(ID, 텍스트, 선택지→다음 ID) 정도의 단순 테이블로 시작하고, 실제로 분기가 복잡해지면 그때 툴을 고민.

## 7. 구현 순서 제안

1. `StoryFlags`, `OverlayGate` (각각 20줄 이내, 선행 의존성 없음)
2. `InteractionOutline`에 `OverlayGate` 가드 한 줄 추가
3. `IDCheckOverlay` (SYS-04+05 통합) — 가장 먼저 코어 루프가 성립하는 데 필요
4. `DialogueOverlay` (SYS-03/10 겸용)
5. `DayPhaseManager` — 위 오버레이들이 하나둘 붙고 나서 "완료 조건→다음 페이즈"를 마지막에 배선

이 순서는 기능정의서 6장의 MVP 우선순위(SYS-01,02,03,04,05,06,11,12)와도 맞음.
