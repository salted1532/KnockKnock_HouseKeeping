# 넉넉 하우스키핑 프로젝트 종합 진단

작성일: 2026-09-11  
대상: 현재 작업 폴더의 코드·씬·프리팹·데이터·패키지·프로젝트 설정·기획 문서  
방법: 정적 코드 검토, 직렬화 설정 대조, 파일 및 참조 검색. 게임 코드와 에셋은 수정하지 않았다.

## 1. 총평

**상호작용과 접객을 체험할 수 있는 프로토타입의 기반은 잘 잡혀 있다. 그러나 여러 날을 연속 플레이할 때의 상태 일관성과, 판단에 따른 공포 게임의 결과 루프는 아직 부족하다. 현재 상태를 출시 가능한 게임으로 평가하기는 어렵다.**

가장 먼저 손볼 것은 그래픽 추가나 NPC 수 확대가 아니라 **열쇠 수명주기, 입력·화면 잠금, 시퀀스 취소, 하루 진행의 예외 경로**다. 이 부분이 안정되지 않으면 콘텐츠가 늘어날수록 버그 재현과 수정 비용이 커진다.

| 관점 | 평가 | 판단 근거 |
|---|---|---|
| 게임 정체성 | 명확함 | 불완전한 정보로 숙박객을 판단하고 다음날 결과를 확인하는 모텔 운영 공포 |
| 코드 분리 | 좋은 출발 | Interactable / Effect / Condition, NPC 정의와 대사 데이터 분리 |
| 실행 안정성 | 우선 보강 필요 | 전역 상태와 코루틴 정리가 분산되고 복수 잠금의 소유권이 없음 |
| 게임 규칙 완결성 | 미완성 | 행동력 제한 우회, 열쇠 반환 부재, 밤 판정·엔딩 미연결 |
| 콘텐츠 제작 체계 | 소규모에는 적합 | CSV 임포트가 있으나 실패 시 원본 DB 보존·일차별 분기 검증 부족 |
| 보안 | 확인된 원격 침해 취약점 없음 | 자체 게임 코드의 외부 입력면은 작음. 개발 도구와 의존성 관리가 주요 검토 대상 |
| 성능 | 측정 필요 | 무제한 생성은 확실한 위험. 일반 HUD 폴링이 실제 병목인지는 미측정 |
| 배포·QA | 부족 | 자체 자동 테스트/CI 구성 미발견, 배포 씬에 디버그 옵션 활성 |

**“전체 파일 확인”은 전체 파일 구조·유형·주요 참조를 조사했다는 뜻이다. 모든 이미지·모델·음원·외부 라이브러리 바이너리를 하나씩 열어 시각·청각 또는 역공학 검증한 것은 아니다.** Library·Logs·UserSettings는 원본 소스와 구분했으며, Library는 설치된 개발 도구의 구현 확인에 한정해 참고했다.

### 검증 한계

- 아래의 “확인”은 코드나 직렬화 데이터에서 확인했다는 뜻이다. 플레이 모드에서 재현 완료했다는 뜻이 아니다.
- `dotnet build Assembly-CSharp.csproj --no-restore --nologo -v:q`는 `NETSDK1004`로 종료됐다. 생성된 프로젝트의 `Temp/obj/Assembly-CSharp/project.assets.json`이 없어 C# 컴파일 단계에 도달하지 못했다. **코드 컴파일 오류를 발견한 것으로 해석하면 안 된다.**
- Unity Player 빌드, 실제 플레이, FPS/메모리 프로파일링, 침투 테스트는 수행하지 않았다.
- 패키지의 최신 버전·알려진 CVE·외부 서비스 보안은 이번 로컬 검토의 검증 범위가 아니다. 특정 패키지가 취약하다고 단정하지 않는다.

우선순위: **P1** = 다음 안정화 작업에 포함, **P2** = 콘텐츠 확대·외부 테스트 전 개선, **P3** = 측정 또는 장기 정리. 출시를 막는 미구현 기능은 버그와 따로 표시한다.

## 4. 코드 및 게임 진행 문제

### C01. 열쇠의 수명주기가 체크인에서 끝난다 — P1

**근거:** `Assets/My/Scripts/Interaction/Effects/CheckInGuestEffect.cs:39`, `Game/GuestManager.cs:69`, `Interaction/RoomController.cs:88` (뒤의 두 경로도 `Assets/My/Scripts` 아래).

체크인 시 `RemoveActiveItem()`으로 슬롯을 비우고 월드 열쇠를 `Destroy`한다. 체크아웃은 GuestState를 목록에서 지울 뿐 열쇠를 반환·재생성하지 않는다. HookEffect도 시작 시의 열쇠 배치만 제공한다. 확인한 자체 코드에는 체크아웃에 연결된 열쇠 복구 경로가 없다.

**영향:** 같은 객실을 다시 판매할 수 있어도 열쇠 실물이 줄어든다. 초기 열쇠를 모두 쓰면 신규 체크인을 계속 진행하기 어렵다. 만실 여부와 별개의 장기 플레이 장애다.

**개선:** 열쇠를 파괴되는 소모품이 아니라 객실 자산으로 모델링한다. `보관함 → 플레이어 → 투숙객 → 체크아웃 반환` 상태를 두고, 입실 승인 및 퇴실 처리와 연결한다. 떨어뜨린 열쇠·분실·사망 시 반환 정책도 정의한다.

**검증:** 같은 방에 입실→퇴실→재입실을 반복하고, 누적 10회를 넘는 체크인 후에도 열쇠를 회수해 계속 진행할 수 있는지 확인한다.

### C02. 행동력이 탐문 제한으로 작동하지 않는다 — P1

**근거:** `Interaction/Effects/KnockEffect.cs:130`, `Game/ActionPoints.cs`, `Interaction/Conditions/ActionPointsDepletedCondition.cs:7`, `Dialogue/QuestionPanel.cs`, `Inventory/InventorySystem.cs:175`.

- KnockEffect는 시작할 때 행동력이 남았는지 검사하지 않는다. 대화 완료 시에만 `Use(1)`을 호출하며, 0이면 차감만 무시된다. 따라서 0에서도 추가 탐문을 시작할 수 있다.
- `QuestionPanel.CanAsk` 훅은 있지만 자체 코드에서 이를 할당하는 경로가 발견되지 않았다.
- 반대로 취침은 행동력 0이 필수다. 손님 전원 거절·전원 노크 거부 상태에서는 대화로 소진할 방법이 없다.
- 현재 Can_Coke는 행동력 전체 소진 기능이 있어 우회 가능하다. 따라서 “항상 영구 소프트락”은 아니다. 다만 정상 진행이 특정 소비 아이템의 존재·접근성에 의존한다.
- 동일 손님에게 다시 노크하면 토픽 기록이 초기화된다. 끝까지 듣기 직전 ESC로 나가면 정보를 듣고도 행동력을 보존할 수 있다. 이는 버그 여부보다 자원 설계 결정을 요구한다.

**개선:** 탐문 시작 시 소모 예약/가용량 확인, 유효 정보 획득 시 소비 등 비용 부과 시점을 명확히 한다. 남은 행동력을 버리고 취침하는 정식 행동을 제공하고, 행동력은 “다 써야 하는 숙제”보다 정보 획득의 한도로 쓰는 편이 자연스럽다.

**검증:** 0 AP 탐문 차단, 손님 0명 취침, 전원 노크 거부, 동일 손님 반복, ESC 취소 시 비용 규칙을 각각 검사한다.

### C03. 브리핑의 전역 Playing이 다음 게임까지 남을 수 있다 — P1

**근거:** `Game/NightNewsBriefing.cs:50,88`, `Game/PauseMenu.cs:39`, `Interaction/Interactable.cs:73`.

Playing은 static이며 정상 코루틴 마지막에서만 false가 된다. OnDisable/OnDestroy/재시작 초기화가 없다. PauseMenu는 브리핑 자체를 ESC 소비자로 취급하지 않아 브리핑 중 메뉴로 나가는 경로가 있다.

**조건과 영향:** 브리핑 진행 중 메인 메뉴로 이동하면 씬 코루틴이 끝까지 실행되지 않는다. 같은 실행 프로세스에서 다시 InGame에 들어와도 Playing이 true로 남아 `Interactable.CanInteract`가 모든 상호작용을 막을 수 있다. Editor 도메인 리로드 설정만의 문제가 아니라 런타임 씬 재진입 문제다.

**개선:** 시작·완료·취소·씬 언로드를 하나의 종료 루틴으로 모은다. Playing 초기화뿐 아니라 숨긴 HUD, TV, 플레이어 잠금도 해당 시퀀스의 소유 범위에서 복구한다.

**검증:** 브리핑 시작/타이핑/슬라이드 사이/종료 페이드 각각에서 메인 메뉴로 나간 뒤 재시작한다.

### C04. 접객 종료 시 이동 코루틴이 페이드 잠금을 해제한다 — P1

**근거:** `Game/ReceptionManager.cs:392`, `Interaction/Modes/UIInteractionMode.cs:312`, `Game/DayPhaseManager.cs`, `Assets/Scenes/InGame.unity:43846,44254`.

EndSession은 `ExitAll()`로 복귀 이동을 시작한 직후 `Advance()`로 페이드를 시작한다. Teardown 완료 콜백은 FirstPersonController와 GazeInteractor를 무조건 다시 켠다. 새로 걸린 FrozenForOverlay를 검사하지 않는다.

씬에서는 복귀 이동 0.3초, 페이드아웃 0.4초·유지 0.1초·페이드인 0.6초다. 즉 페이드가 진행 중인 시점에 복귀 이동 콜백이 먼저 입력을 풀 수 있다.

**개선:** 복귀 이동을 마친 뒤 페이드를 시작하거나, 이동 완료는 위치 복구만 담당하고 최종 입력 활성 여부는 공통 잠금 관리자가 결정하게 한다.

**검증:** 마지막 손님 퇴장 직후 이동키·E를 누르고, 페이드가 완전히 끝나기 전 위치나 상호작용 상태가 변하지 않는지 확인한다.

### C05. ESC 소비와 중첩 잠금이 실행 순서에 의존한다 — P1

**근거:** `Game/PauseMenu.cs:39,46`, `Interaction/Modes/UIInteractionMode.cs:253`, `Interaction/Effects/ShowPanelEffect.cs`.

UIInteractionMode가 먼저 ESC로 모니터/노크 스택을 pop하면, 뒤에 실행된 PauseMenu는 이미 바뀐 TopEscExits를 읽어 같은 ESC로 메뉴까지 열 수 있다. 두 스크립트의 meta에는 실행 순서 지정이 없었다. ShowPanelEffect에는 `lastCloseFrame` 방어가 있지만 앵커 종료에는 없다.

또한 FreezeForOverlay는 bool 하나다. 이미 잠금 상태일 때 다른 오버레이가 잠금을 요청하면 무시하지만, 나중에 어느 쪽이든 false를 호출하면 잠금이 해제된다. 예를 들어 페이드/브리핑 중 일시정지를 열었다 닫는 경우 원래 잠금의 소유권이 보존되지 않는다. PauseMenu도 이전 Paused 상태와 timeScale을 저장하지 않고 false/1로 복원한다.

**개선:** 한 프레임의 ESC를 한 곳에서 처리하고, `Pause`, `Dialogue`, `Transition`, `Note` 등의 잠금 소유자를 토큰 또는 상태 스택으로 관리한다. 입력 상태는 활성 소유자 전체로부터 계산한다.

**검증:** 모니터 ESC 1회, 노크 ESC 1회, 접객 일시 이탈 후 Pause 열기/닫기, 페이드 중 Pause 열기/닫기를 반복한다.

### C06. 디버그 동작이 배포 씬에 활성화되어 있다 — P1

**근거:** `Assets/Scenes/InGame.unity:43800` testShuffleAllGuests=1, `:43825` debugEndKey=1, `:43868` debugAdvanceKey=1.

N/Q/K 처리가 Editor 또는 Development Build로 제한되어 있지 않다. 배포 씬에서도 업무·대화·단계 게이트를 건너뛸 수 있다. 특히 저녁에 N/Q로 페이즈만 바꿔도 ReceptionManager는 저녁 이탈을 정리하지 않아 접객 상태가 남을 수 있다. 테스트 셔플은 Campaign의 일차 편성을 무시한다.

**개선:** 개발 전용 컴파일 가드와 빌드 전 설정 검증을 함께 적용한다. 디버그 전환도 시퀀스 취소를 거치는 경로로 통일한다. 단순히 디버그 키만 끄기 전에 C07의 빈 편성 처리를 해결해야 한다.

이것은 싱글플레이 규칙 무결성 문제이며, 이를 원격 해킹 취약점으로 부풀릴 필요는 없다.

### C07. 편성이 비어 있으면 저녁에 머문다 — P2

**근거:** `Game/ReceptionManager.cs:121,146`, `Assets/My/Scripts/Dialogue/Campaign.asset`.

**개선:** “오늘 손님 없음”은 정상 결과로 정의해 세션 종료 또는 마감 행동을 제공한다. 필수 prefab/catalog 누락은 다른 오류로 분리하여 시작 전 검증한다.

### C08. 같은 ItemId 두 개가 하나의 손 오브젝트를 공유한다 — P2

**근거:** `Inventory/HandItemRegistry.cs`, `Inventory/InventorySystem.cs:79,221`.

Registry는 ItemId당 GameObject 하나를 돌려준다. AddItem은 중복을 막지 않아 두 슬롯이 같은 GameObject를 저장할 수 있다. 첫 소다를 활성 슬롯에 둔 상태로 두 번째 소다를 주우면 새 비활성 슬롯의 `SetActive(false)`가 현재 손의 소다도 끈다.

**개선:** 슬롯은 itemId·수량·월드 인스턴스 등 데이터만 저장하고, 손 표현은 활성 슬롯 하나에서 갱신한다. 스택 또는 개별 인스턴스 정책을 정한다. 여러 평행 배열도 InventorySlot 구조체/클래스로 합치는 편이 안전하다.

추가로 UseActiveItem은 `useClip == null`이면 아이템 효과 자체를 실행하지 않는다(`:166`). 효과음 누락이 기능 불능으로 이어지지 않도록 사운드와 사용 로직을 분리한다. 현재 소다에는 클립이 있어 이 문제를 현재 소다의 고장으로 단정하지 않는다.

### C09. 손님 이동이 목표를 지나칠 수 있다 — P2

**근거:** `Dialogue/GuestMover.cs:78`, `Assets/My/InGame/Prefabs/Guest.prefab:203`.

남은 거리와 무관하게 `speed * deltaTime`만큼 이동한다. 기본 speed=1.3, 도착 반경=0.06이다. 예를 들어 10 FPS에서는 한 프레임 0.13 이동하며, 목표까지 0.065인 위치에서는 목표 양쪽을 왕복하면서 반경 0.06 안에 못 들어갈 수 있다.

**개선:** MoveTowards 또는 남은 거리로 이동량을 제한한다. 경로가 막히는 경우와 잘못된 speed/웨이포인트에 대한 타임아웃·진단도 추가한다. 현재 웨이포인트 연출 규모라면 즉시 NavMesh로 전면 교체할 필요는 없다.

**검증:** 10/15/30/60 FPS 및 프레임 지연 조건에서 접객 큐 완주 여부를 검사한다.

### C10. 코루틴 중단이 시퀀스 종료를 보장하지 않는다 — P2

**근거:** `Interaction/Effects/KnockEffect.cs:45`, `Game/ReceptionManager.cs:415`, `Dialogue/DialogueRunner.cs`.

KnockEffect.OnDisable은 코루틴을 중단하고 busy만 초기화한다. 코루틴 지역변수에 있는 guest 제거, 문 닫기, DialogueRunner.Cancel, 자기 앵커 해제는 마지막 정리 블록에만 있다. 따라서 실행 도중 오브젝트를 끄면 정리가 생략된다.

접객 StopQueue도 DialogueRunner를 취소하지 않는다. K 종료 등에서 공용 대화 패널이나 질문 상태가 남을 수 있다. DialogueRunner.Cancel은 기다리던 결과 콜백을 호출하지 않아 외부 WaitUntil과 결합하면 무한 대기가 가능하다. Play/SayNode의 중복 실행도 세션별 상태 분리가 없다.

**개선:** 시퀀스 컨텍스트가 생성 오브젝트·대화 핸들·앵커를 보유하고, 정상/취소/실패 결과를 정확히 한 번 전달하게 한다. 모든 종료 경로가 동일 Cleanup을 호출하도록 한다.

### C11. 열쇠 종류와 배정 객실의 번호를 비교하지 않는다 — P2

**근거:** `Interaction/Effects/CheckInGuestEffect.cs`, `Inventory/ItemId.cs`, `Game/GuestManager.cs:51`.

Key101~Key110 식별자는 존재하지만 체크인은 IsKey와 PendingRoom>0만 검사한다. 101호 열쇠를 110호 손님에게 주어도 승인된다. 코드 주석에도 후속 구현으로 명시된 부분이다.

또한 최종 GuestManager.CheckIn에는 객실 존재·중복 점유·유효 NPC 검증이 없다. UI에서 한 번 확인하더라도 최종 상태 변경 함수가 규칙을 보장해야 한다.

**개선:** `TryCheckIn(npc, room, key)`에서 검증과 열쇠 이동·입실·결제 처리를 하나의 성공 단위로 다룬다. 실패하면 열쇠와 돈이 바뀌지 않아야 한다.

### C12. 자판기의 생성량과 추적 목록에 상한이 없다 — P2

**근거:** `Interaction/Effects/SpawnObjectEffect.cs:16`, `Assets/My/InGame/Prefabs/Item/Vending_machine.prefab:187`.

현재 maxCount=0은 무제한이며 쿨다운·비용 검사가 없다. 특히 `spawned.RemoveAll`이 maxCount>0일 때만 실행되어, 무제한 설정에서는 생성물이 파괴되어도 목록의 참조 항목이 계속 누적된다.

**영향:** 반복 입력으로 물리 오브젝트와 추적 목록이 늘어난다. 소다의 행동력 전체 소진과 결합하면 자원 설계도 약해진다. 실제 FPS 저하 임계값은 측정하지 않았다.

**개선:** 재고·쿨다운·동시 생성 상한을 정하고, 무제한이면 추적 자체를 생략하거나 항상 정리한다. 과도한 생성에 대한 성능 검증을 추가한다.

## 5. 데이터 및 아키텍처 문제

### D01. CSV 임포트를 검증 후 반영 방식으로 바꿔야 한다 — P2

**근거:** `Dialogue/Editor/DialogueImporter.cs:35,130`.

임포터는 기존 entries를 먼저 비운 뒤 파일을 읽고, 잘못된 행은 경고 후 건너뛰고 저장한다. 열거형 오타도 기본값으로 조용히 변환된다. 검증은 끊긴 goto를 경고할 뿐 저장을 중단하지 않는다. 파일 정렬이 없고 같은 키의 연속행으로 노드를 합치기 때문에 파일/행 배치에 영향을 받는다.

**개선:** 임시 데이터에 파싱→필수 열·enum·중복키·NPC 존재·일차별 goto·도달 가능성 검사→오류 0일 때 기존 SO에 반영한다. 실패 시 이전 DB를 보존하고 파일명/행번호/오류를 한 번에 출력한다. CSV 수정 후 임포트를 빠뜨린 상태도 빌드 전에 검출한다.

### D02. 다른 일차 대사가 잘못 반환될 수 있다 — P2

**근거:** `Dialogue/DialogueDatabase.cs:70`.

GetNode는 오늘 전용도 공통 day=0도 없으면 `list[0]`을 반환한다. 3일차에만 있어야 할 노드가 1일차에 재생될 수 있다. 임포터 goto 검증도 NPC/상황/키만 검사하며 일차 적합성을 검사하지 않는다.

**개선:** 오늘→공통→없음으로 조회를 끝내고, 특정 날짜를 넘어가는 분기는 명시적 규칙으로 만든다. Query의 “해당 role에 전용이 하나라도 있으면 공통 전체 제외” 역시 의도된 덮어쓰기 단위인지 문서화한다.

### D03. 상태 변경이 화면·객실 연출 코드에 분산되어 있다 — P2

RoomController.Apply가 문·침대 연출뿐 아니라 후불 정산과 체크아웃도 수행한다. ReceptionManager는 큐·걷기·대화·방배정·요금 선택·정산을 함께 담당한다. 상태 저장소 GuestManager는 public 가변 GuestState를 노출한다.

**문제:** 객실 오브젝트 활성 여부나 이벤트 호출 시점이 경제 상태를 결정한다. 저장/불러오기, 사망 처리, 씬 분할을 추가하면 연출 복원과 정산 재실행을 분리하기 어려워진다.

**개선:** 소규모 서비스부터 추출한다. 예: 객실/투숙 상태, 입퇴실 및 정산, 밤 결과 계산. RoomController는 확정된 상태를 표시하고, ReceptionManager는 시퀀스 진행을 맡는다. 모든 코드를 대형 프레임워크로 다시 작성할 필요는 없다.

### D04. 초기화·이벤트·static 관리가 일관되지 않다 — P2

Wallet/ActionPoints/ShowPanelEffect는 static 초기화 방어가 있지만 여러 매니저는 Awake에서 Instance만 지정한다. 여러 시스템이 Start 구독에 의존하며, 일부만 현재 상태를 즉시 적용한다. 비활성 오브젝트·씬 재진입·중복 매니저 상황의 규칙이 통일되어 있지 않다.

특히 SpriteLightResponse의 정적 라이트 목록과 `lightsRefreshedAt`은 Time.time을 사용한다. 새 씬에서 시간이 초기화되면 이전 갱신 시각까지 새 라이트 수집이 지연될 수 있다(`Environment/SpriteLightResponse.cs:61`).

**개선:** 중복 인스턴스 정책, 구독/해제 대상 보관, 시작 상태 적용, 씬 변경 시 캐시 무효화를 공통 규약으로 정한다. static 초기화만 무조건 추가하는 대신 실제 수명 범위를 결정한다.

### D05. 설정 오류를 조용히 넘기는 경로가 많다 — P2

- GazeInteractor는 playerCamera가 없으면 즉시 예외를 낼 수 있다. 반면 CursorInteractor에는 null 가드가 이미 있다.
- PickupEffect는 손 오브젝트를 못 찾으면 경고 후 월드 아이템을 없앤다. 연출용 줍기와 설정 실수를 구분할 필요가 있다.
- PhaseCondition은 매니저가 없으면 통과하고, 다른 업무 게이트는 매니저가 없으면 차단한다.
- 슬롯 UI 배열 길이, 캠페인 데이터, 질문 버튼 prefab, SpeechBubble.label 등 필수 참조의 통합 검증기가 없다.

**개선:** 빌드 전에 필수 컴포넌트·객실 번호 유일성·아이템 Registry·배열 길이·조건 연결을 검사한다. 런타임에서 늦게 조용히 실패하기보다 콘텐츠 제작 단계에서 위치를 알려준다.

## 6. 게임 시스템과 기획 평가

### 장점

1. **공간과 판단이 연결된다.** 접객에서 본 사람을 새벽 문틈에서 다시 만나는 구조는 모텔이라는 무대를 잘 활용한다.
2. **콘텐츠 확장 기반이 있다.** Effect/Condition 조합과 CSV/SO 분리 덕분에 새로운 조사 대상·대화·연출을 추가할 수 있다.
3. **진행 안내가 준비되어 있다.** 할일 HUD, 목표 마커, 단계 페이드가 플레이어의 길 찾기를 돕는다.
4. **작업 기록이 풍부하다.** 기능이 현재 형태가 된 이유를 추적하기 좋다.

### 가장 큰 공백: 판단 → 사건 → 다음날 결과

NpcData 9명의 `isSleepwalker`는 현재 모두 0이다. 자체 스크립트에서 이 값을 읽어 밤 생존 결과를 계산하는 구현은 발견되지 않았다. README도 밤 판정·살해·게임오버·엔딩을 미구현으로 적고 있다. Campaign은 1일차 데이터만 있고 TV 슬라이드는 빈 배열이다.

이는 “이미 구현된 기능의 버그”가 아니라 **핵심 가치 검증을 아직 마치지 못한 상태**다. 현 상태만으로 판별의 재미, 불확실성의 공정성, 경제와 생존의 균형을 평가할 수 없다.

**권장 최소 완성 범위:** 3일치 고정 캠페인, 정상/위협 손님 혼합, 잘못된 승인과 거절의 다음날 결과, 간단한 생존/실패 엔딩, 일차 시작 체크포인트. 이 범위에서 먼저 재미를 확인한 다음 NPC 60명으로 늘린다.

### 규칙과 난수 정책을 먼저 정해야 한다

- 정상 0명·위협 0명, 동수, 위협이 더 많음 등 경계 조건의 밤 판정표를 작성한다.
- 힌트 신뢰도와 실제 정답의 관계를 정의한다. 모든 단서가 임의적이면 플레이어는 추론이 아니라 운으로 느낄 수 있다.
- 반복 테스트를 위해 손님 편성과 밤 판정의 난수 seed를 기록한다. 현재 셔플·침대·환경 연출이 Unity 전역 Random을 사용하므로 연출 변경이 결과 재현에 영향을 줄 수 있다.
- 밤 판정 결과를 데이터로 먼저 확정한 뒤 연출한다. 뉴스/사망 연출 재생을 재시도해도 결과가 다시 추첨되면 안 된다.

### 경제는 아직 수입 표시 단계에 가깝다

Wallet은 Add만 제공하고, 상점 구매·지출 제약·운영비·부족 시 결과는 연결되지 않았다. 선불/후불이 둘 다 확정 수입이라면 현금 흐름과 미수 위험이 없을 때 선택의 의미가 약하다. 시스템이 확장될 때 `TrySpend`, 잔액 검증, 정산 중복 방지와 선택별 대가를 설계한다.

### 저장/복구와 플레이 편의

자체 코드에서 게임 저장·불러오기 경로는 발견되지 않았다. 하루가 여러 단계로 길어지는 게임이므로, 메인 메뉴 복귀나 종료 시 손실되는 진행의 범위를 정해야 한다. 초기에는 전 상태의 임의 시점 저장보다 “새날 시작” 저장이 상태 복원 난도를 낮춘다.

현재 PauseMenu는 메인 메뉴 복귀 중심이다. 외부 플레이테스트 전에는 볼륨, 마우스 감도, 자막 크기, 깜박임/화면 흔들림 완화, 키 안내를 준비하는 편이 좋다. 이는 현재 요청 사양을 어긴 버그가 아니라 접근성과 배포 준비 개선안이다.

## 7. 보안과 의존성 관리

### 현재 확인된 사실

- 자체 게임 코드의 위험 API 검색에서 서버 연결, 외부 명령 실행, BinaryFormatter 역직렬화, 인증 토큰 처리 경로는 발견되지 않았다. 로컬 CSV 읽기는 Editor 임포터에 있다.
- 이 결과는 **비밀정보 또는 취약점이 전혀 없다는 보증이 아니다.** Git 전체 이력·바이너리·모든 외부 패키지 내부까지 정밀 감사하지 않았다.
- `.uloop/settings.permissions.json`은 `allowThirdPartyTools=false`, `dynamicCodeSecurityLevel=1`이다. 설치된 패키지 enum에서 1은 Restricted다.
- 설치된 uloop의 `Editor/Server/McpBridgeServer.cs:197`은 `IPAddress.Loopback`으로 리스닝한다. 현재 근거로 “인터넷 전체에 서버가 노출됨”이라고 주장할 수 없다.
- 패키지 manifest의 uloop Git URL에는 revision 지정이 없지만 packages-lock에는 커밋 hash가 있다. 따라서 현재 해석된 의존성은 기록되어 있고, 무조건 매 실행마다 최신 코드를 받는 상태는 아니다.

### 개선할 부분

| 항목 | 위험/한계 | 권장 조치 |
|---|---|---|
| 개발 도구의 실행 권한 | Restricted라도 Unity 오브젝트·에셋 조작 기능은 강력함 | 현재 제한 모드를 유지하고 외부 자료의 코드를 그대로 실행하지 않는 작업 원칙 유지 |
| 의존성 재현성 | lock 재생성 또는 명시적 업데이트 시 Git 브랜치 최신 코드가 달라질 수 있음 | manifest에도 검토한 commit/tag를 고정하고 lock 변경을 리뷰 |
| 공급망 검토 | 버전 고정은 코드 신뢰성 검증과 별개 | 패키지 도입 이유·출처·버전·업데이트 담당·로컬 패치를 기록 |
| 로컬 관리 서버 | Loopback은 외부 노출을 줄이지만 로컬 요청 신뢰까지 증명하지 않음 | 인증·요청 검증·수명 관리 필요성은 별도 확인. 취약점 확인 전 RCE로 단정 금지 |
| 배포용 파일 분리 | 개발 도구 설정·로그·원본 데이터가 배포물에 섞일 가능성 | 실제 Player 산출물을 검사하고 개발 파일 포함 여부 확인 |
| 비밀정보 추적 | `.gitignore`에 비밀 파일 전용 정책은 제한적 | 향후 키 도입 시 .env·인증서·자격 증명 파일 제외 및 CI secret scan |

싱글플레이의 `isSleepwalker` 정답이나 잔액은 클라이언트에 존재하므로 역분석으로 볼 수 있다. 현재 범위에서 이를 막기 위한 서버 도입·강한 안티치트는 우선순위가 낮다. 실제 개인정보·계정·결제를 추가한다면 그때 신뢰 경계를 새로 설계해야 한다.

## 8. 성능·에셋·운영 품질

### 성능

- **우선 해결:** C12의 무제한 생성과 목록 누적.
- **측정 후 개선:** MorningTasks/LunchTasks/MonitorRoomBoard가 매 프레임 목록을 순회하고 문자열·UI 속성을 갱신한다. 현 규모에서는 병목이라고 단정할 수 없지만, 값이 바뀔 때만 갱신하면 불필요한 할당과 갱신을 줄일 수 있다.
- **렌더링:** 실시간 조명, 스프라이트 조명 근사, RenderTexture 픽셀화, 아웃라인 비용을 함께 측정해야 한다. 화면이 픽셀화된다고 원본 텍스처 메모리나 그림자 비용까지 자동으로 작아지는 것은 아니다.
- **물리:** 던지기의 SphereCastAll, 다수 소다 Rigidbody, 카트 정렬은 각각 프로파일링한다. 카트의 transform.forward 정렬을 단순히 up으로 치환하면 안 된다. 모델 축을 씬에서 검증해야 한다.
- **좌표 변환:** CursorInteractor와 RenderTextureGraphicRaycaster의 화면 밖 검사는 이미 보간값을 얻은 뒤 비교한다. 실제 RawImage 영역 포함 판정과 레터박스/화면비 테스트를 추가하는 것이 안전하다.

측정 기준: 목표 PC를 정하고 MainScene→InGame 전환 시간, 평균/하위 FPS, 프레임당 GC, GPU 메모리, 3일 반복 플레이 전후 메모리, 소다 다량 생성 조건을 기록한다.

### 에셋과 저장소

전체 Assets는 약 1.16 GiB이며 8K EXR 약 43 MiB, 50 MiB 이상 glb 등 큰 원본이 있다. **이 크기는 Player 배포 크기나 런타임 메모리가 아니다.** 참조되지 않은 에셋까지 배포에 포함된다고 단정할 수 없다.

2,683개 프리팹과 원본 에셋 팩, 샘플 씬은 제작 편의를 주지만 탐색·임포트·버전 관리 비용도 만든다. 의존성 목록과 Build Report로 실제 사용분을 확인한 뒤 정리한다. 원본 팩·샘플을 이름만 보고 일괄 삭제하지 않는다. 큰 바이너리의 변경 빈도를 보고 LFS 도입 여부를 정한다.

### 에디터 도구와 유지보수

- AssetOrganizer는 `DryRun=false`가 기본이다(`Assets/Editor/AssetOrganizer.cs:23`). 메뉴 실행으로 광범위한 생성/이동이 일어날 수 있으므로 미리보기와 적용 단계를 나누고 변경 목록을 출력하는 편이 안전하다.
- FontTool/StripTestRoomProBuilder처럼 prefab contents를 열고 저장하는 도구는 예외 발생 시에도 unload되도록 finally를 보장한다.
- StripTestRoomProBuilder는 패키지 내부 타입·메서드에 reflection으로 접근하므로 버전 변경 시 취약하다. 타입/메서드 존재 검사를 추가한다.
- Assets에서 자체 asmdef 및 정식 EditMode/PlayMode 테스트 구성을 발견하지 못했다. DialogueImporter와 SpriteLightResponse에는 수동 SelfCheck가 있으므로 “테스트가 전혀 없다”는 평가는 부정확하다.
- README의 CursorInteractor null 예외, Interactor.Owner 탐색 반복 등 일부 지적은 현재 코드와 맞지 않는다. 현 코드는 CursorInteractor null 가드와 Owner 폴백 캐시가 있다. 문서의 문제 목록에도 확인일·해결 여부를 표시하는 것이 좋다.
- 외부 에셋의 구매/배포 권한과 라이선스 증빙은 저장소만으로 확인되지 않는다. 이를 위반으로 판정하지 않고, 배포 전 확인 항목으로 관리한다.

## 9. 권장 개선 순서와 완료 기준

### 1단계: 하루 루프 안정화

1. C01 열쇠 반환과 C11 방 번호 대조를 하나의 입퇴실 규칙으로 정리한다.
2. C02 행동력 게이트와 손님 없는 밤의 정식 종료를 만든다.
3. C03~C05, C10의 잠금·취소·씬 재시작을 통합 정리한다.
4. C06 디버그 동작을 개발 전용으로 제한하고 C07 빈 편성을 처리한다.
5. C08·C09·C12를 수정한다.

완료 기준: 디버그 키 없이 3일 이상 진행, 누적 10회 이상 입퇴실, 모든 손님 거절, 노크 전원 거부, 모든 주요 화면에서 메뉴 복귀→재시작이 가능하다.

### 2단계: 콘텐츠 제작 안전장치

CSV 검증 후 반영, 일차별 노드 검사, 필수 씬 배선 검증, 데이터 ID 유일성 검사, 자동 테스트를 구축한다. 변경이 없는 데이터는 재임포트해도 의미가 같아야 하고 오류 CSV는 기존 DB를 훼손하지 않아야 한다.

### 3단계: 최소 공포 루프 완성

3일 캠페인·밤 판정·결과 연출·간단 엔딩·체크포인트를 연결한다. 판별 근거와 다음날 결과의 관계가 플레이어에게 전달되는지 관찰한다. 이 단계가 끝나기 전 대량 NPC 제작은 투자 효율이 낮다.

### 4단계: 배포 품질

타깃 기기 프로파일링, 옵션/접근성, 빌드 검증 자동화, 의존성/에셋 출처 정리, 외부 테스트를 진행한다.

### 우선 작성할 회귀 검사

| 검사 | 기대 결과 |
|---|---|
| 같은 객실 재입실·잘못된 열쇠 전달 | 올바른 키만 승인되고 퇴실 시 키 회수 |
| 0 AP·손님 0명·노크 전원 거부 | 규칙에 맞게 제한하고 항상 정상 취침 경로 제공 |
| 브리핑 도중 메뉴 복귀 후 새 게임 | Playing/커서/입력/HUD가 초기 상태 |
| 모니터 ESC 한 번 | 모니터만 닫히고 Pause는 열리지 않음 |
| 접객 종료 중 이동·상호작용 입력 | 전환 완료 전 차단 |
| 같은 소다 두 개 소지·슬롯 교환·사용 | 슬롯별 데이터와 손 표현 일치 |

| 비개발 Player에서 N/Q/K | 디버그 전환이 실행되지 않음 |

## 10. 최종 판단

잘 분리된 상호작용 기반과 접객 연출은 유지할 가치가 높다. 전면 재작성보다 **상태 변경과 시퀀스 종료의 책임을 정리하고, 여러 날의 진행을 보장하는 것**이 효과적이다. 그 위에 밤 판정과 다음날 결과를 연결해야 이 프로젝트의 고유한 재미를 검증할 수 있다.
